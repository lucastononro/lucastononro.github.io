There are three honest reasons [`pr-brief`](https://github.com/lucastononro/pr-brief) exists, and none of them are noble.

First, I had to review enormous pull requests and I was not in a position to ask everyone to break them up and stack them. Second, reviewing a big PR is needle-in-haystack work, and the needles are not evenly distributed — I wanted to know the right *order* to look. Third, reading code is not the hard part; connecting the dots between files is. A migration in one folder, a cache read in another, a controller that flips the flag in a third. Holding that graph in your head is the actual work, and it is the part that gets skipped at file 140.

So the skill does the connecting and hands you the result.

## What it does

You ask Claude Code to "review this pr" and it fetches the PR with `gh`, then an Opus agent does three things before you see anything:

1. **Groups every changed file into features** with a markdown description each — not by folder, by what the change is *for*.
2. **Computes a review sequence** — migrations before the code that reads them, tests last.
3. **Authors a narrative layer**, which is the part I actually care about.

Then it opens a local page at `localhost:7681` with GitHub-style stacked diffs, and the narrative sits in a track to the right of the code.

## Two kinds of pill

The narrative comes in two flavours, and keeping them separate is most of the design.

**Explain pills** (purple ✨) tell you what the code does and why it is written that way. The rule in the skill definition is that each one must do at least three of four jobs: what changed, why it changed, *where it connects*, and what to watch for. That third job is the one that matters — a pill has to name a specific call site by `path:symbol`.[^connect] A pill that could belong to any PR is a bad pill.

[^connect]: The instruction in `SKILL.md` is blunt about this: pills are planned together as one connected story, first pill grounds the feature, mid pills reference earlier features by name, last pill hands off to whatever consumes it. Read in sequence they should leave you understanding the whole change, not twelve isolated snippets.

**Critique pills** (red ⚠) tell you what is wrong with it. Each carries a severity S1–S5, and the skill spends a lot of words on calibration, because a severity scale that is not calibrated is just decoration:

> If everything is S5, nothing is. If everything is S1, you've added noise.

The guidance is that a typical fifty-file PR has zero S5s, one to three S4s, five to ten S3s, and more of the small stuff — and that files which are genuinely fine should get no critique at all. Forced critiques are worse than silence. Every critique pill has a **Use as comment →** button that opens the inline editor pre-filled with the text, plus a GitHub `suggestion` block when the agent proposed a concrete fix.

## The bits I am smug about

**Comments post in realtime.** No batch submit step. Every saved inline comment goes straight to GitHub through `gh api`, with the diff `position` values pre-computed at build time so the mapping from "line I dragged over" to "position GitHub understands" is settled before the browser opens.

**Click-and-drag multi-line selection.** Because review comments are almost never about one line.

**Inline chat that already knows the PR.** Select code in a diff, right-click, and a streaming chat panel opens on the right. The trick is that every panel — across snippets, across files, across page reloads — resumes *the same Claude Code session that wrote the brief*:

```bash
claude --resume <session-id>
```

The skill writes the resumable id to `~/.claude/pr-review/pr-<num>/session.json` at run time. So the chat starts with the entire PR in context: no re-seeding, no vector store, no separate persistence layer. Cross-snippet follow-ups like "compare this with the previous file" just work, because it is one conversation the whole time.[^degrade] That was the cheapest good idea in the project by a wide margin.

[^degrade]: And if capture fails for any reason, the right-click menu simply never appears and everything else keeps working. Optional features should fail invisibly.

## Shape of the thing

The whole plugin is a `SKILL.md`, one HTML file, and a Python stdlib server:

```
plugins/pr-brief/skills/pr-brief/
├── SKILL.md            # the definition: grouping, sequencing, pill rules
└── templates/
    ├── index.html      # the UI
    └── server.py       # local HTTP server, standard library only
```

No build step, no `node_modules`, no framework. It runs locally and the only outbound call is to the Anthropic API your Claude Code session was already talking to. Artifacts land in `~/.claude/pr-review/pr-<num>/`; the repository under review is never touched.

Install it as a marketplace plugin:

```
/plugin marketplace add lucastononro/pr-brief
/plugin install pr-brief@pr-brief-marketplace
```

---

The thing I did not expect: the feature grouping turned out to be more valuable than the pills. Being told "these nine files are one idea, read them in this order, then these four are a second idea" removes most of the cognitive load of a big PR before any AI commentary enters the picture. The narrative is the nice part. The ordering is the useful part.
