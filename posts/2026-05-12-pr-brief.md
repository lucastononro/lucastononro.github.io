Three honest reasons [pr-brief](https://github.com/lucastononro/pr-brief) exists. I had to review enormous PRs and couldn't ask everyone to stack them. The needles in that haystack are not evenly distributed, so I wanted to know the right *order* to look. And reading code isn't the hard part — connecting a migration in one folder to a cache read in another is, and that's the part you skip at file 140.

[“PR Brief skill” — the whole loop.](https://www.youtube.com/watch?v=9d9u7UEAgLU&t=4s)

## Two kinds of pill

Ask Claude to "review this pr" and an Opus agent groups every changed file into a feature, orders them (migrations first, tests last), and writes the narrative layer that sits beside the diff.

**Explain pills** say what the code does. The rule: each must name a specific call site by `path:symbol`. A pill that could belong to any PR is a bad pill.

**Critique pills** say what's wrong, with a severity S1–S5. The skill spends more words on calibration than on anything else, because an uncalibrated scale is decoration:

> If everything is S5, nothing is. If everything is S1, you've added noise.

Vague critiques are banned outright — name the cleanup or skip the pill. Any critique converts to a real inline comment in one click.[^post]

[^post]: Comments POST to GitHub the moment you save them, with diff `position` values pre-computed at build time. No batch submit step.

## Chat that already knows

![Select code in a diff, right-click, and a chat panel opens on the right](/images/pr-brief-inline-chat.jpg)

Every chat panel resumes *the same Claude Code session that wrote the brief* — `claude --resume <id>`. So it starts with the whole PR in context. No re-seeding, no vector store, and follow-ups like "compare this with the previous file" just work.

The whole plugin is 524 lines of `SKILL.md`, one HTML file, and a stdlib Python server. No `node_modules`.
